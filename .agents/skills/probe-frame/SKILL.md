# probe-frame — 문제 정의

지침 파일(`~/probe-kit/AGENTS.md`, 킷을 다른 곳에 뒀으면 그 경로)을 새 세션이거나 대화가 압축됐거나 지침이 불확실하면 먼저 다시 읽는다.

## 먼저 판단: 빠른 경로인가
README에 목표·데이터·제출 형식·평가 기준이 이미 구체적이면 이 단계는 과제 시간의 5% 안에 끝낸다: 요약 → 미확인 1~3개만 질문 → BRIEF. 절차를 채우려고 시간을 쓰지 않는다.

## 순서
1. 읽기만 한다: README, 디렉터리, 데이터 파일 이름·크기·형식, 제출물 형식과 경로, 과제가 지정한 문서·파일명. 구현하지 않는다.
   - 실행 환경도 이때 셸로 본다(읽기 전용): `git --version; date '+%F %T %Z %z'; python3 -V; node -v; npm -v`
     데이터 과제면 `python3 -c "import pandas, sklearn; print('pkgs ok')"`도 본다.
   - 없다고 나온 것만 대체를 정해 결정 절에 한 줄: pandas 없음 → 표준 `csv` 모듈이나 SQL, sklearn 없음 → 규칙·통계 기준선, git 명령 없음 → commit 대신 결과 파일·로그로 증거를 남기고 재사용하지 않음(저장소만 없으면 `git init`). 과제에 필요한 실행 환경 자체가 없으면 사용자와 대체를 정한다. 새 설치는 승인 후에만(AGENTS 2).
   - `date`의 오프셋이 `+0900`(KST)이 아니면 종료·35%·제출 시작 시각을 서버 시각으로도 BRIEF에 적는다. UTC면 KST 10:00이 01:00으로 찍힌다.
2. 한 단계 위 질문을 한 문장으로 쓴다: "이 과제가 실제로 답하려는 업무 질문은 무엇이고, 그 답으로 누가 무엇을 결정하나?"
3. 사용자에게 보고한다: 요청 한 문장 / 과제 유형 / 제출물(README 문구 그대로) / README만으로 확정되지 않는 것 최대 5개.
   - 과제 유형은 셋 중 하나: 예측(모델 학습) / 집계·분석(표·그림으로 답) / 구현(기능·파이프라인·웹 앱). 섞였으면 주 산출물 기준. 예측이 아니면 타깃·분할을 정하지 않는다.
4. 업무 담당자에게 물을 질문 후보를 영향이 큰 순서로 만든다. 질문은 사용자가 메신저의 업무 담당자(실무자 에이전트)에게 직접 보낸다. 화면 사용법·제출 절차 질문은 Cofa Helper로.
   - 1순위, 답에 따라 구조가 바뀌는 것: 한 행의 의미와 기록 시점, 타깃·판정 기준(임계값과 같은 값이면 통과인지), 최근 실제 사례 한 건과 지금 처리하는 방식, 사람이 꼭 판단해야 하는 지점, 성공 숫자, 놓치는 것과 잘못 알리는 것 중 더 비싼 쪽, 처리 한도(하루 몇 건 검사·조치 가능)·지연·설명 필요 같은 운영 제약, 결과물을 누가 어디에 쓰는지.
   - 2순위, 처리 정책: 결측·이상값·중복 처리, 빼야 할 데이터(취소·테스트 등), 단위·코드값의 의미.
   - 3순위, 이름·서식처럼 되돌리기 쉬운 것: 묻지 않고 정한다.
   - 큰 질문 대신 작은 사실 질문부터 한다. 요구가 한 번에 다 나오지 않을 수 있으니 업무 판단에 필요한 미확인 사실을 하나씩 구체적으로 묻고, 받은 답을 다음 결정에 반영한다. 할 일 목록을 통째로 요청하지 않는다.
   - 업무 흐름이 문서·기존 답으로 확인되지 않았으면 첫 질문 후보: "지금 이 일은 어떤 순서로 하세요? 제일 번거로운 대목은요?" 무엇을 물을지 모르겠으면 "이 일에서 어떤 내용까지 여쭤볼 수 있나요?"(답할 수 있는 범위를 알려 준다).
   - 묻는 요령(킷 권장): 한 메시지에 질문 1~2개, 개발 용어 대신 현장 말("파일 첫 줄에 적힌 건 뭐예요?"), 숫자·시각·실제 사례로 묻는다. 담당자가 파일·화면을 본다고 가정하지 않고 필요한 내용을 짧게 설명한다(개인정보·비밀값 제외). 같은 질문을 반복하지 않는다.
   - 숨은 요구 점검표 — 전부 묻는 목록이 아니라 질문 후보다. 문서·자료·기존 답으로 확정되지 않고 구현·검증을 바꾸는 업무 기준만 대화로 확인한다(담당자 대화도 평가 기록으로 수집된다):
     ① 사람이 정할 것: 도구가 대신 결정·단정하면 안 되는 것, 누가 최종 확인하나, 해제·종료가 곧 처리 완료인가
     ② 만들지 말 것: 실시간 연동·자동 발송·대시보드·로그인·AI 원인 분석처럼 담당자가 원하지 않는 범위
     ③ 자료 함정: 문서·기준표가 여러 판이면 어느 것이 현행이고 언제부터인가, 단위·시간대·형식이 파일마다 같은가, 같은 일이 반복·연쇄·재측정되면 몇 건인가, 빼야 할 대상(정비 중·시험용)
     ④ 경계: 기준값과 같으면, 기간 시작·끝 정각이면, 적용 시각 정각이면 어느 쪽인가
     ⑤ 성공 기준: 지금 얼마나 걸리나·몇 번 놓치나(현재값) → 목표값 → 어디서 재나(측정 위치). 예: "다 만들고 나서 뭐가 달라지면 '쓸 만하다'고 보실까요?"
     ⑥ 사용 환경: 실제로 쓸 PC·브라우저, 인터넷, 설치 가능 여부, 결과를 저장해도 되나, 어떻게 전달받나(개발 환경과 따로 묻는다)
     ⑦ 출력 형식: 어디에 붙이나, 섹션 순서, 줄 수 제한과 넘칠 때, 시각·단위 표기, 표 가능 여부
     ⑧ 민감정보: 결과에 이름·사번·전화번호를 넣어도 되나, 파일 첫 줄·비고의 접속 정보·비밀번호는 어떻게 다뤄야 하나(값 자체는 대화에 쓰지 않는다)
   - 과제가 준 초안 문서(PRD 등)의 가정을 한 줄씩 뽑아 담당자에게 맞는지 확인한다. 틀린 가정은 그 문서에서 고친다.
   - 파일·데이터로 명확히 확인되는 사실은 묻지 않고 직접 본다. 의미·기준·예외가 모호하거나 문서와 실제가 충돌할 때 담당자에게 묻는다.
   - 질문마다 답에 따라 바뀌는 결정과, 답이 오기 전 임시 가정(또는 '답변 전 보류')을 한 줄 붙인다. 담당자 확인 전 구현 금지(7)는 그대로다.
   - 남은 질문이 처음 만들 것을 바꾸지 않으면 멈춘다. 보통 3~6개로 시작하고, 데이터를 본 뒤 생긴 확인 질문을 이어서 한다.
5. 사용자에게 현장·도메인 경험이 있으면, AI가 사용자를 짧게 인터뷰해 가정을 끌어낸다. 한 번에 한 질문, 최대 3개, 선택지 2~4개.
6. 받은 답을 반영해 BRIEF를 쓴다(과제가 문서를 정했으면 그 문서, 아니면 `NOTES.md`). BRIEF 합의를 요청하는 같은 메시지에 probe-stack A의 기술 후보 표를 붙인다(`$probe-stack`이 안 불리면 `~/probe-kit/.agents/skills/probe-stack/SKILL.md`의 A절을 읽는다. 따로 멈추지 않는다).
   - `[사용자]` 표시 줄(업무 질문·성공 기준·버린 것과 이유)은 사용자가 정한다. AI는 후보를 낼 수 있지만 사용자가 프롬프트에 쓴 말로 채운다. "좋아"만 했으면 무엇을 왜 고르는지 한 번 묻는다.
   - 결정에 쓴 담당자 답은 짧게 인용해 근거로 남긴다(예: "세 번 넘게 반복하면 답을 외운다" → 재시도 2회 제한).
   - 답을 듣고 문제를 다시 정했으면 "다시 정한 문제" 한 줄로 쓴다.
   - 버릴 것과 이유를 적는다. 내가 낸 안을 담당자가 뺀 것도 포함한다.
   - 답에 근거한 항목과 `[가정]`을 구분한다.
7. 사용자와 한 번 합의한 뒤(요약 끝에 "제가 놓친 중요한 게 있을까요?"를 한 번 붙인다), 합의 요약 3줄(다시 정한 문제·성공 기준·이번에 안 하는 것)을 사용자가 업무 담당자에게 보내 확인받는다(prompt.md ③-1). 답을 기다리는 동안은 data-check(읽기 전용)만 진행하고 구현은 시작하지 않는다. 답이 10분 넘게 없으면 사용자가 진행할지 정한다. 답으로 바뀐 것은 BRIEF와 담당자 답 인용에 반영한다. 그다음 `.gitignore`(`.env`·키·큰 원본·중간 데이터·`outputs/logs/`. 제출물과 `outputs/` 결과물은 넣지 않는다)를 만든 뒤 commit: `frame: 문제 정의 합의`. 이후에는 AGENTS 1번의 멈춤 조건에 걸릴 때만 다시 묻는다.

## NOTES.md 형식 (과제가 문서를 정했으면 그 안에 같은 내용을. 과제에 해당하는 줄만 채운다)
```
# NOTES
## BRIEF
- 과제 유형(예측 | 집계·분석 | 구현):
- 업무 질문(누가 무엇을 결정하나) [사용자]:
- 요청(한 문장) / 다시 정한 문제:
- 성공 기준 [사용자](현재값(알 때만) → 목표값 또는 통과 조건 / 어디서 재나·무엇으로 확인하나 / 출처: 담당자 답 | README | [가정]):
- 평가 지표(과제 지정 | 틀렸을 때 더 비싼 쪽으로 선택):
- 한다 / 버린 것과 이유 [사용자]:
- 담당자 답 인용(결정 근거):
- 제출물(형식·경로·컬럼):
- 기술·뼈대(probe-stack, 고른 것 / 버린 대안):
- 시각표 (KST · 서버 시각): 35% 첫 완주 / 70% 확정·검증 우선(새 실험 먼저 제안 안 함) / wrap 시작(85% 또는 읽기 시작 − 최종 실행 소요 − 10분 중 이른 때) / 읽기(종료 15분 전) / 제출 시작(종료 10분 전) / 종료:
- 가정:
### 데이터 (probe-data-check에서 채움)
## 결정
| 시각 | 결정 | 근거 | 버린 대안 | 위험 |
## 실험
| # | 바꾼 것 | 가설 | 지표(검증) | 기준선 대비 | 판정 | 근거(명령·결과 파일·코드 파일:줄) |
## 인계
(첫 완주 때: 현재 상태 / 실행 명령 / 소요시간. 전체 양식은 probe-wrap 3)
```

## 하지 말 것
- 질문의 답을 추측으로 채우기. 모르면 `[가정]`.
- README를 그대로 옮겨 적기. 요약하고 미확인을 드러낸다.
- 이 단계에서 모델·라이브러리를 정하기.
- 사용자 대신 업무 질문·성공 기준·버린 것을 확정하기.
