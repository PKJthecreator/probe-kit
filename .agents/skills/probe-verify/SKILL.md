# probe-verify — 증거로 확인하기

지침 파일(`~/probe-kit/AGENTS.md`, 킷을 다른 곳에 뒀으면 그 경로)을 새 세션이거나 대화가 압축됐거나 지침이 불확실하면 먼저 다시 읽는다.

## 완료 게이트 (주장마다)
1. 이 주장을 증명하는 명령과 결과 파일은 무엇인가
2. 증거로 쓸 실행은 commit한 뒤 돌리고, 로그 첫 줄에 commit·명령, 끝에 종료 코드를 남긴다.
   - 예: `mkdir -p outputs/logs; { echo "commit=$(git rev-parse --short HEAD) dirty=$(git status --porcelain | wc -l) cmd=python3 train.py"; python3 train.py; echo "exit=$?"; } > outputs/logs/base.log 2>&1`
   - 로그는 `outputs/logs/`에 쓰고 이 폴더만 `.gitignore`에 넣는다. 안 그러면 방금 만든 로그 파일 때문에 `dirty`가 0이 되지 않는다. 표·그림 같은 결과 파일은 `outputs/`에 두고 코드와 함께 commit한 뒤 돌린다.
   - 실행 뒤 `git status --short`가 다시 비었는지 본다. 바뀐 파일·새 파일이 있으면 commit된 상태와 이번 실행 결과가 다르다는 뜻이다. 원인(commit 누락·seed·실행 시각 같은 변동 값)을 고치고(변동 값은 결과 파일 대신 로그에) commit한 뒤 다시 돌린다. 마무리 단계에서는 probe-wrap 3을 따른다.
   - 다시 쓰는 조건: 로그의 commit이 지금 `git rev-parse --short HEAD`와 같고, 로그의 `dirty=0`이고, 지금 `git status --porcelain`이 비었고, 명령이 같고, `.gitignore`에 든 데이터·설정을 그 뒤에 바꾸지 않았고, 패키지·런타임을 설치·변경하지 않았다. 하나라도 불확실하면 다시 돌린다.
   - 제출 직전 최종 검증은 재사용하지 않고 새로 한 번 돌린다(probe-wrap 3).
3. 전체 재실행은 인계 절에 적어 둔 소요시간을 보고 계획한다. 마감 전에 끝날 수 있을 때 미리 시작한다. 끝까지 못 돌 것 같으면 대표 입력으로 줄인 실행으로 증거를 남기고, 전체 실행은 NOT_RUN(사유)으로 적는다.
4. 출력을 끝까지 읽는다: 종료 코드, 경고, 행 수, 지표. 정상 종료여도 실행된 검사가 0건이거나 전부 skip이면 NOT_RUN, 수집·실행 오류는 FAIL이다. 결과가 원래 0건이어야 하는 경우는 그 기대값을 검사로 확인한다.
5. 판정은 `PASS` / `FAIL` / `NOT_RUN` / `HUMAN_CHECK`(사람이 눈으로 봐야 함) 중 하나

| 주장 | 필요한 증거 |
|---|---|
| 스크립트가 돈다 | 실행 명령, exit 0, 실행 로그 파일 |
| 숫자가 맞다 | 결과 파일의 값 + 다른 방법으로 재계산해 일치(groupby 대 수동 필터, 표본 몇 행 손계산) |
| 개선됐다 | 같은 분할·지표·seed로 기준선과 나란히 비교한 결과 파일 |
| 제출물이 맞다 | README의 형식·경로·컬럼·행 수와 한 줄씩 대조 |
| 요구를 충족했다 | BRIEF의 성공 기준을 체크리스트로 하나씩 |
| 화면이 동작한다 | 사용자가 Browser 도구에서 직접 확인(`HUMAN_CHECK`), 서버 로그 |
| 담당자 환경에서 열린다 | 설치·서버 없이 여는 산출물이면 `file://`로 열어 제공 데이터로 돌린 결과(또는 사용자 `HUMAN_CHECK`) |
| 업무 기준과 맞는다(교차 확인) | 제공 데이터의 한 구간을 손으로 대조한 표, 또는 비밀값·개인정보를 뺀 출력 예를 담당자에게 보여 받은 확인 답 |
| 한 번에 점검 | `sh ~/probe-kit/templates/harness/gate.sh --exclude <원본 폴더> --test "<과제 테스트 명령>" [--sample sample.csv 제출.csv]`: 지정한 테스트·비밀값·제출 형식을 각각 PASS/FAIL/NOT_RUN과 로그로(전부 skip·0개는 NOT_RUN). 각 항목의 근거는 아래 줄대로 따로 읽는다 |
| 비밀값·개인정보를 옮기지 않았다 | `check_secrets.py --exclude <원본 폴더>`(작업 트리 + git 이력, 사번 형식은 `--pattern`)가 PASS **그리고** data-check에서 적어 둔 민감 위치(파일 첫 줄·이름·비고 열)의 값이 출력·문서·테스트·로그에 없는지 직접 확인. PASS는 "그 패턴으로 못 찾았다"는 뜻일 뿐이고 .gitignore로 뺀 로그는 따로 본다 |

담당자에게(결과의 업무 적합성이 아직 확인 안 됐을 때만): "이 입력에서 이렇게 나왔습니다: {짧은 예, 개인정보·비밀값 뺌}. 기대하신 것과 맞나요?" / "평소엔 잘돼도 이 상황만큼은 틀리면 안 된다는 경우가 있나요?"(답 → 경계·실패 테스트 추가) / 오류 안내 문구가 있으면 "이 문구를 보면 다음에 뭘 하실지 분명한가요?". 담당자의 동의는 업무 기준 확인일 뿐 실행 증거를 대신하지 않는다.

핵심 결과의 증거는 세 가지를 함께 적는다: `명령` / `outputs/의 결과 파일` / `계산 코드 파일:줄`

증거의 종류를 섞지 않는다: 단위 테스트, 끝까지 도는 실행(E2E), 실제 연결 확인(live), 짧은 시험 실행(smoke)을 따로 적는다. 가짜 데이터나 mock으로 대신했으면 그렇다고 밝히고, 그 결과를 실제 성공으로 보고하지 않는다. 실제 연결이 안 되면 `NOT_RUN`(사유)으로 남긴다.

## 데이터 과제 추가 점검
- 단계마다 행 수가 예상과 같은가(조인·필터 전후)
- 입력 컬럼이 모두 예측 시점에 알 수 있는 것인가
- 내부 holdout을 최종 확정 전에 평가하지 않았는가
- 결과가 지나치게 좋으면 누수부터 의심한다
- 전체 결과와 그룹별 결과가 같은 방향인가

## 구현 과제 추가 점검
- 빌드·테스트가 깨끗한 작업 트리에서 통과하는가
- 과제가 준 실제 입력으로 실행해 출력을 확인했는가
- 빈 값·잘못된 값·경계 입력에 죽지 않는가
- 판정 기준값이 한 파일에 모여 있는가
- 비밀값·개인정보가 코드·출력·git 이력에 없는가
- 과제 지정 문서(없으면 README)의 실행 방법대로 처음부터 실행되는가

## 사전 부검 — 최종 검증에 포함, 합쳐 10분 이내(상한)
"이 결론이 틀린 것으로 밝혀졌다면 가장 그럴듯한 이유 2가지는?"
이유마다 확인할 명령이나 표를 하나씩 정해 실행한다. 이미 유효한 증거가 있으면 그것을 가리키고, 못 한 것은 `NOT_RUN`, 화면으로만 볼 수 있는 것은 사용자에게 `HUMAN_CHECK`로 넘긴다.

## 실패했을 때 — 원인 먼저
1. 오류 메시지와 스택을 끝까지 읽는다
2. 가장 작은 입력으로 재현한다
3. 직전 변경을 `git diff`로 본다
4. 원인 후보 1~3개와 각각의 확인 방법을 적고 확인한다
5. 원인 지점만 고친다 → 같은 입력으로 재실행 → 수정 전후를 비교한다 → 고친 테스트·영향받는 경로·첫 완주 핵심 경로의 짧은 검사를 다시 돌린다(전체 재실행은 완료 게이트 3)
6. 프롬프트·규칙·지시를 바꿔서 고쳤다면 결정 절에 무엇을 왜 바꿨는지 남기고, 같은 검증을 다시 통과시킨다.
두 번 고쳐도 같은 실패면 멈추고 사용자에게 상황과 가설을 보고한다. 모델·API·플랫폼 오류가 반복되면 사용자가 상단 "문제 신고"로 알린다(키·토큰은 적지 않는다).

## 결과가 원하던 것이 아닐 때
BRIEF(요청)·만든 것·원하는 것을 비교해, 처음 어긋난 지점을 한 문장으로 쓴다: "{지점}에서 {X}를 가정했는데 실제로는 {Y}였다."
원인 종류에 따라 처리한다.
- 말하지 않은 가정 → BRIEF에 기준을 추가한다
- 묻지 않은 질문 → 업무 담당자 질문을 준비한다
- 데이터·도메인이 예상 밖 → probe-data-check를 다시 한다
- 지시가 너무 구체적이거나 너무 막연 → 의도와 기준을 다시 쓴다
어긋난 부분만 다시 하고, 살릴 수 있는 부분은 살린다.

## 보고 형식
probe-stack B의 현업 수준 체크를 같은 보고에 한 줄로 붙인다(`STACK | 체크 n/m ✓ | ✗: …`). 필수 항목이 `✗`면 FAIL, 확인 못 했으면 NOT_RUN이고 완료로 쓰지 않는다.
`VERIFY | 실행 PASS (outputs/logs/run.log, commit=…) | 재계산 PASS | 기준선 대비 … | 요구 n/m | NOT_RUN: … | [추론] …`
