# probe-wrap — 마무리와 설명 준비

지침 파일(`~/probe-kit/AGENTS.md`, 킷을 다른 곳에 뒀으면 그 경로)을 새 세션이거나 대화가 압축됐거나 지침이 불확실하면 먼저 다시 읽는다.

사용자가 "연습"이라고 하지 않으면 실전 모드다.

## 실전 모드 — 순서대로, 앞 단계가 끝나야 다음으로

### 1. 동결 (85% 또는 '읽기 시작 − 최종 실행 소요시간 − 10분' 중 이른 때)
- 새 실험·리팩터링을 멈춘다.
- 제출 판단을 바꿀 미확인 사항이 남았을 때만 담당자에게 마지막 확인(답은 인계 절에): "제가 이해한 사용 흐름은 {요약}입니다. 다르게 이해한 곳이 있나요?" / "{미구현·제한}이 남았는데 이 상태로 쓰면 가장 곤란한 상황이 뭘까요?" 새로 드러난 필수 누락·중대 오류는 남은 시간과 수정 위험을 보고 사용자가 정하고, 추가 기능은 한계·다음 할 일로 남긴다.

### 2. 제출물 확인 (최우선)
- README·과제 안내가 요구한 필수 파일·문서·형식·경로·컬럼·행 수와 한 줄씩 대조한다.
- 제출 파일이 최종 확정한 코드·모델·설정으로 만든 것인지 확인한다(생성 명령·commit을 실험 절 최종 줄·인계 절과 대조). 첫 완주 이후 코드·모델·설정·입력이 바뀌었거나 생성 근거를 확인할 수 없으면 최종 확정본으로 재생성하고 검증한다.
- TODO·FIXME·미구현 표시는 문맥을 보고 템플릿 잔재면 정리한다. 반쯤 만든 기능은 제거하거나 꺼 두고 인계 절 한계에 적는다. 필수 요구를 못 채웠으면 FAIL로 남긴다(표시만 지워 감추지 않는다).
- 처음부터 재실행하는 명령 한 줄을 결과 문서 맨 위에 둔다.
- 결론은 10줄 이내, 순서는 질문 → 답 → 근거 숫자(결과 파일·코드 위치) → 한계.

### 3. 인계 절과 최종 검증
첫 완주 때 만든 인계 절을 이 양식으로 채운다.
```
## 인계
### 현재 상태
### 실행 방법 (명령, 소요시간)
### 누가 무엇을
- 내가 정한 것 (기준·범위·버린 것):
- AI가 만든 것:
- 내가 확인한 것 (검증과 결과 파일):
### 아직 모르는 것·한계 (NOT_RUN, 대신 쓴 데이터·mock 포함)
### 다음에 할 일 (우선순위 3개)
```
- 과제가 `docs/` 문서(PRD·ARCHITECTURE·DECISIONS·ROADMAP 등)를 줬으면 템플릿 그대로인 문서가 없는지 본다: PRD = 합의한 요구·범위 밖·성공 기준(현재값·목표값·측정 위치)·제약·경계 판단표·정정한 초안 가정, ARCHITECTURE = 구조와 실행 방법, DECISIONS = 결정·버린 대안·약점, ROADMAP = 놓치거나 타협한 요구·한계·다음 할 일·측정 계획.
- 인계 절 "현재 상태"에 최종 검증 로그 경로(`outputs/logs/final.log`)를 미리 적고 commit: `wrap: 제출물·인계 정리`
- 그 commit에서 최종 산출물을 probe-verify 2의 방식으로 새로 한 번 돌려 `outputs/logs/final.log`에 남긴다(재사용하지 않는다). 실행 뒤 `git status --short`가 비었는지 본다. 바뀐 파일·새 파일이 있으면 무엇이 왜 바뀌었는지 보고하고, 다시 commit·실행할지는 사용자가 정한다. 다시 돌리지 않으면 최종 검증을 PASS로 적지 않고 변경 내용과 함께 보고한다. 그 뒤로는 추적되는 파일을 고치지 않는다. 결과는 로그로만 남고, 사용자에게는 대화로 보고한다.

### 4. 설명 메모 — 읽기 시간 전에 여유가 있을 때만
- 후속 서술형 문항은 제출물과 작업 기록(AI 대화, 터미널, git 로그·diff, 테스트 결과, 작업 공간 파일)으로 만들어진다. 그 기준으로 예상 질문(최대 6개)과 질문마다 답의 뼈대 한 줄을 만든다.
- 뼈대: ① 내 산출물의 구체 지점(파일·숫자) ② 왜 그렇게 했고 무엇을 버렸나 ③ 무엇으로 확인했고(실제 있었던 실패와 원인 포함) 남은 한계는 무엇인가.
- probe-kit 뼈대를 가져왔다면 "뼈대에서 온 부분 / 과제에 맞게 바꾼 부분 / 직접 새로 쓴 부분"을 한 줄로 구분해 둔다(질문받으면 그대로 설명한다).
- 메모는 `outputs/logs/explain.md`에 두거나 대화로 보여 준다(3절 뒤에는 추적 파일을 고치지 않는다). 채점은 하지 않는다. 사용자가 읽고 머릿속으로 정리하는 용도다.

### 5. 직접 읽기 — 종료 15분 전부터 10분 전까지
- 후속 서술형은 AI 없이, 복사·붙여넣기 없이 직접 입력한다. 확정 뒤에 파일을 다시 볼 수 있는지는 확인되지 않았으니 [미확인] 이 시간에 읽는다.
- 사용자는 기록 문서의 BRIEF·결정·인계와 설명 메모를 읽는다: 무엇을 왜 골랐나, 버린 대안과 근거 숫자, 검증 결과, 남은 한계.
- AI는 이 시간에 새 작업을 하지 않는다.

### 6. 제출 → 확정 → 후속 서술형 → 완료 (종료 10분 전 시작, 사용자가 화면에서)
AI는 아래 순서를 사용자에게 한 번 안내하고 새 작업을 하지 않는다.
1. 에디터 탭이 모두 "저장됨"인지 본다. "외부 변경 감지"가 뜨면 양쪽 내용을 비교한 뒤 "외부 변경 불러오기"나 "현재 내용으로 저장"을 고른다. 필수 파일 경로를 다시 본다.
2. 상단 "제출하고 문제풀기" → 미리보기. 미리보기는 파일 일부만 보여 준다(숨김 파일 등 생략 가능). 고칠 게 있으면 닫고 고친다.
3. "제출물 확정하고 문제풀기". 이후 파일 수정 불가. 질문 준비 대기(약 5분, 화면상 최대 10분이고 자동 재시도되면 다시 늘어날 수 있다)는 답변 시간이 아니다.
4. 후속 서술형: 첫 문장에 결론을 쓰고 근거·한계를 덧붙인다. 문항당 5분, 직접 입력, 이전 문항으로 돌아갈 수 없고, 시간이 끝나면 현재 답이 자동 확정된다. 빈 답으로는 직접 다음 문항으로 넘어갈 수 없다. 질문의 전제가 실제 구현과 다르면 차이를 밝히고 내가 한 것을 설명한다. 모르면 지어내지 않고 "모른다, 이렇게 확인하겠다"로 답한다.
5. 마지막 "답안 제출하고 마치기" → 처리·업로드가 끝날 때까지 기다린다 → "과제가 잘 제출됐어요." 화면에서 제출 ID·시각·파일 수·크기를 확인하고 브라우저를 닫는다.

## 연습 모드 — 사용자가 "연습"이라고 할 때 (시험 전)
코드·기록 문서·git 로그와 diff·테스트 결과·실행 로그를 읽고 후속 서술형처럼 6문항을 만든다(실제 문항 수는 응시 화면 안내를 따른다). 파일 이름이나 숫자를 외웠는지 묻지 않고, 동작과 판단을 묻는다.
- 입력 상황: "이런 데이터·요청이 들어오면 지금 결과는 어떻게 되나?"
- 경계: "결측·0·중복·새 범주·다른 기간·잘못된 입력이면?"
- 실패: "이 결론이 틀렸다면 가장 먼저 의심할 곳은?"
- 이탈: 결정 절의 이탈·위임 항목마다 하나. "왜 계획과 다르게 했나?"
- 선택: "이 지표·분할·모델·구조를 고른 이유와 버린 대안은?"
- 흐름: "입력이 결과가 되기까지 어떤 파일·함수를 어떤 순서로 지나나?"
- 요구 대응: "담당자 요구 중 놓쳤거나 타협한 것은? 이유와 보완 계획은?"
- 운영 위험: "내일부터 쓰면 가장 큰 위험은? 무엇으로(어디서 재서) 확인하나?"
- 지시 변경: "AI에게 준 지시를 바꾼 뒤 결과가 어떻게 달라졌고, 무엇으로 확인했나?"
- 승인: AI가 낸 안을 그대로 받아들인 곳 하나. "왜 맞다고 봤고, 무엇으로 확인했나?"
- 6문항 중 하나는 전제를 실제 구현과 살짝 다르게 낸다. 사용자가 그 차이를 짚는지 본다.

진행 방법:
1. 질문을 한 번에 하나만 보여준다.
2. 사용자는 5분 안에 직접 타이핑해 답한다. 답하는 동안 AI 도움·붙여넣기 없이. 답을 받으면 바로 다음 질문(이전 질문으로 돌아가지 않는다).
3. 6문항이 끝나면 보고서가 아니라 코드와 결과 파일에 대조해 채점한다.
4. 틀리거나 흐린 답은 `파일:줄`로 설명하고, 같은 개념을 다른 상황으로 바꾼 질문을 한 번 더 낸다.

답할 때는 직접 본 것과 추정한 것을 구분해서 말한다. 코드와 어긋나는 유창한 답이 가장 나쁘다. 모르면 지어내지 말고 "모른다, 이렇게 확인하겠다"로 답한다. 이 원칙은 실전 후속 서술형에도 그대로 쓴다.
