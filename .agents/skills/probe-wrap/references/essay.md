# 서술형 대비 — 어떤 과제든 같은 틀 (probe-wrap 4·연습 모드가 읽는다)

후속 서술형은 내 제출물과 작업 기록(AI 대화·터미널·git 로그와 diff·테스트·작업 파일)에서 나온다. 주제가 바뀌어도 묻는 **축**은 같다. 축마다 답의 재료가 작업 중 NOTES 어디에 쌓이는지 정해 두고, 빈 축은 마무리 전에 채운다.

## 1. 서술형이 묻는 9축과 재료 위치
| 축 | 이런 질문으로 나온다 | 재료(NOTES·기록) |
|---|---|---|
| ① 결과 | 무엇을 만들었고 결론은 무엇인가 | 인계 '현재 상태', 결과 파일 |
| ② 흐름 | 입력이 결과가 되기까지 어떤 파일·함수를 어떤 순서로 지나나 | 인계 흐름 한 줄 `입력 → 검증 → 처리 → 저장 → 응답·화면` |
| ③ 모듈 | 각 파일·모듈은 무슨 일을 하나, 어디를 고치면 무엇이 바뀌나 | 인계 모듈 지도 `파일:함수 — 역할 — 확인 테스트` |
| ④ 기법 | 왜 이 기법·도구를 썼나, **흔히 떠올릴 대안은 왜 안 썼나** | 결정 절(버린 대안·근거) + 아래 2절 표 |
| ⑤ 데이터·규칙 | 결측·중복·경계값·단위·제외 대상을 어떻게 정했나, 근거는 | data-check 표, 경계 판단표, 담당자 답 인용 |
| ⑥ 검증 | 무엇으로 맞다고 확인했나, 숫자는, 못 한 것은 | 실험 절, VERIFY 줄, NOT_RUN·HUMAN_CHECK 목록 |
| ⑦ 장애·역할 | 무엇이 안 됐고 어떻게 고쳤나, **AI가 한 것과 내가 한 것** | 실험 절 장애 행, 결정 절 `[사용자]` 지시 인용, git diff |
| ⑧ 요구·담당자 | 담당자 답으로 무엇이 바뀌었나, 놓치거나 타협한 요구는 | BRIEF 담당자 답 인용, 버린 것, 결정 절 이탈 줄 |
| ⑨ 한계·운영 | 내일부터 쓰면 가장 큰 위험, 보안·개인정보, 다음에 할 일 | 인계 한계·다음 할 일, check_secrets 결과 |

## 2. 과제 유형별 "왜 X를 썼나/안 썼나" 후보 — 고를 때 결정 절에 한 줄씩
고를 때 이 표의 해당 행에서 **이 과제에 해당하는 대안**만 골라 `버린 대안: {X}, 이유: {데이터·요구·시간 사실}`로 적는다. 비교 실험을 안 했으면 "비교했다"고 쓰지 않는다("{이유} 때문에 시도하지 않았다").
| 과제 유형 | 흔히 묻는 선택 | 답에 들어갈 사실 |
|---|---|---|
| 예측(분류·회귀) | 딥러닝 vs 부스팅·선형, 불균형 처리(오버샘플링 vs 가중치·임계값), 분할(무작위 vs 시간·그룹), 지표(정확도 vs 재현율·PR-AUC·비용), 결측·특성 선택, 하이퍼파라미터 탐색 | 행 수·양성 비율, 예측 시점, 누수 가능성, 기준선 대비 숫자, 시간 |
| 시계열 | LSTM·전용 라이브러리 vs 계절 기준선·부스팅, 백테스트 방식, 지표(MAPE vs WAPE) | 기간 길이, 계절성, 0값 비율, 기준선 대비 |
| 집계·분석 | 통계 검정 여부, 평균 vs 중앙값, 이상치 제거, 군집·차원축소, 인과 단정 | 분모·표본 수, 분포 치우침, 업무 질문이 요구한 것 |
| 이상 탐지·품질(SPC) | 관리도·규칙 vs 모델(이상 점수), 임계값 정한 방법 | 기준 문서·담당자 답, 놓침과 오경보 중 더 비싼 쪽 |
| 웹·업무 앱 | 프레임워크(React·Vue vs 빌드 없는 화면), 인증(세션 vs 토큰), 저장(SQLite vs 서버 DB), 구조(단일 vs 여러 서비스), 실시간(새로고침·폴링 vs 스트리밍), 권한 검사 위치 | 받는 사람 환경, 동시 사용자, 설치·시간, 보안 요구 |
| 챗봇·에이전트·RAG | LLM이 판정할까 규칙·코드로 할까, 검색(키워드 vs 임베딩), 파인튜닝 vs 프롬프트, 근거 없는 답 처리, 평가 세트 | 근거 문서 수, 틀리면 비용, 평가 결과 숫자 |
| 배정·경로·일정 | 군집화, 최적해(전용 솔버·헝가리안) vs 탐욕·규칙, 제약 처리 | 이미 주어진 것(노선·일정), 정원·시간 제약, 설치 가능 여부 |
| 문서·규정 판정 | 조항 규칙 vs LLM 판단, 근거 표시, 충돌 처리 | 조항 수, 예외, 담당자가 최종 확인하는지 |
| 운영(MLOps·DevOps) | 모델 저장소·컨테이너·CI·오케스트레이션을 넣었나 | 과제 요구 문장, 시간, 받는 쪽 환경 |
| 공통 | 공개 뼈대·AI 제안을 그대로 썼나 | 뼈대에서 온 것 / 바꾼 것 / 새로 쓴 것, 복사 commit |

## 3. 답 쓰는 틀 (문항당 5분, 4~6문장)
1. 첫 문장에 결론. 질문의 전제가 실제와 다르면 첫 문장에서 바로잡는다("실제로는 X가 아니라 Y로 처리했다").
2. 내 산출물의 구체 지점: 파일·함수·숫자 하나 이상.
3. 왜 그렇게 했고 무엇을 버렸나(2절의 사실로).
4. 무엇으로 확인했나: 명령·테스트·결과 숫자, 실제로 난 실패와 원인.
5. 남은 한계와 다음에 확인할 것.
- 역할을 묻는 문항: 3~4를 "내가 정하고 지시·확인한 것 / AI가 조사·작성한 것"으로 나눈다. AI가 제안만 하고 내가 검증하지 않은 것을 "내가 결정했다"로 쓰지 않는다.
- 모르면 지어내지 않는다: "확인하지 않았다. {이렇게} 확인하겠다."
- 감점: 코드에 없는 처리를 있다고 하기, 수치·기준값을 구현과 다르게 말하기, 파일·함수 없이 일반론만 길게.

## 4. 설명 카드 (마무리 전에 대화로, 축마다 3줄)
`축 | 한 줄 답 | 근거 위치(파일:줄·결과 파일·NOTES 절)`. 최소판은 ②흐름·④기법·⑦장애·역할 3장, 여유가 있으면 9장 전부. 재료가 없는 축은 `[빈 축]`으로 표시하고 git log·diff·대화에서 찾을 수 있으면 `[사후]`로 채운다. 사용자는 읽기 시간에 이 카드를 읽는다.
