# probe-experiment — 기준선과 실험 반복

지침 파일(`~/probe-kit/AGENTS.md`, 킷을 다른 곳에 뒀으면 그 경로)을 새 세션이거나 대화가 압축됐거나 지침이 불확실하면 먼저 다시 읽는다.

## 0. 과제 유형부터 (BRIEF의 유형)
- 기술·뼈대는 probe-stack A에서 고른 것을 쓴다(BRIEF의 "기술·뼈대" 줄). 아직 안 골랐으면 먼저 고른다. 진행 중 새 층이 필요해지면 probe-stack C(그 층만 한 줄로 묻기).
- 질문에 답하는 집계·비교형 과제면 모델을 만들지 않는다. 답을 뒷받침하는 표와 그림이 산출물이다.
- 기능·파이프라인·웹 앱 구현 과제면 모델 학습 대신 아래를 따른다. 이 경우 1~5번은 해당하는 것만 쓴다.
  - 판정·계산은 코드나 SQL 규칙으로 고정하고, AI(LLM)는 해석·생성만 맡긴다.
  - 업무 담당자가 정한 판정 기준·임계값은 코드에 흩어 두지 않고 한 파일에 모은다(담당자가 고칠 값이다).
  - LLM의 사실 주장·판정은 입력·데이터·규칙 근거가 없으면 버리고 버린 개수를 남긴다. 창작 문구(배너·안내문 등)는 요구 충족·사실 일치·표현 안전성을 확인해 쓴다.
  - 사용자 행동 하나씩: 구현 → 정상·경계·실패 입력 테스트 → 실제 출력·화면 확인 → commit. 새 핵심 판정 규칙은 먼저 테스트를 쓰고 의도한 이유로 실패하는 것을 본 뒤 구현한다. 기대값은 요구 문장·담당자 답·손계산으로 정하고 구현 코드에서 가져오지 않는다.
  - 첫 완주(35%): 핵심 사용자 행동 하나가 입력→출력까지 동작 + 그 행동의 정상·경계·실패 테스트 + 과제 지정 문서(없으면 README)에 실행 방법. 과제가 제출 형식을 정했으면 그 형식으로.
  - 웹 서비스면 서버를 `0.0.0.0`에 바인딩해 전용 터미널에서 띄우고, 실제 포트·경로를 알려 사용자가 Browser 도구에서 직접 눌러 보게 한다(AGENTS 3).
  - 산출물 형태는 **받는 사람의 환경**(frame 점검표 ⑥)으로 정한다. 설치 불가·인터넷 차단이면 런타임 외부 호출(LLM API·CDN·웹폰트)과 브라우저 저장소 없이 `file://`로 열리는 HTML 한 파일(`templates/static-tool`, Vite면 `build.mjs --vite`)로 만들고 실제로 열어 본다.
  - 사람이 정할 것은 도구가 문장으로 만들지 않는다: 판정 필요 항목은 확인 체크(안 하면 `[미확인]`), 해제·종료를 처리 완료로 쓰지 않음, 원인·조치·해제 가능 같은 판단 문장 생성 금지. 사실(상태·수치)만 쓴다.
  - 출력은 담당자가 말한 형식 그대로(섹션 순서·줄 수·넘칠 때 접는 규칙·시각·단위 표기). 메신저용이면 표 없는 일반 텍스트 + 복사 버튼.
  - 잘못된 입력은 조용히 버리지 않는다: 못 읽은 줄·파일·빈 구간·모르는 코드는 건수와 위치로 결과에 적고 나머지는 계속 처리. 전체를 멈추는 조건은 담당자와 정한 것만.
  - 경계 판단표의 규칙마다 상수 한 곳 + 경계 양쪽 테스트(같은 값, 정각, 적용 시각 직전·직후, 단위 변환 후 반올림).
  - 작업을 나눠 맡길 때는 쓰는 파일이 겹치지 않게 하고, 공통 데이터 형식·인터페이스는 메인 세션만 바꾼다.
- 예측 과제면, 먼저 입력 → 예측 → 제출 파일까지 가장 단순한 경로를 한 번 끝까지 돌린다. 제출용 test가 있으면 이때 바로 추론해 제출 파일을 만들고 형식·행 수·ID 순서를 README와 대조한다.
- 첫 완주가 끝나면 인계 절에 현재 상태·실행 명령·소요시간을 적고, probe-stack B 점검을 한 번 한다(AGENTS 2).
- 구현 중 담당자에게(업무 규칙의 새 갈림길이 생겼을 때만. 답이 필요한 결정은 확정하지 않고 겹치지 않는 작업을 한다): "이 경우 {A}로도 {B}로도 할 수 있는데 실제로는 어느 쪽인가요?"(예외 규칙) / "확실하지 않은 결과는 어떻게 표시하고, 누가 확인한 뒤 쓰면 될까요?"(불확실 결과). 추가 요청은 말투가 아니라 목표·필수조건·남은 시간으로 판단한다: 필수 누락·중대 오류는 고치고, 추가 기능은 보류 이유와 함께 다음 할 일로 남긴다.

## 1. 지표
- 과제·README가 평가 지표를 정했으면 그대로 쓴다. 보조 지표는 설명용으로만 덧붙인다.
- 정하지 않았을 때만 BRIEF의 "틀렸을 때 더 비싼 쪽"으로 후보 2개를 제시하고 사용자가 고른다.
  - 놓치는 것이 비싸다 → 재현율(recall). 필요하면 정밀도 하한을 조건으로 둔다
  - 잘못 알리는 것이 비싸다 → 정밀도(precision)
  - 둘이 비슷하다 → F1
  - 검사·조치할 수 있는 수가 정해져 있다(상위 k개만 본다) → precision@k, recall@k
  - 임계값을 아직 정하지 않고 전체 순위를 본다 → ROC-AUC. 양성이 드물면 PR-AUC
  - 회귀 → MAE(오차 크기 그대로) 또는 RMSE(큰 오차에 가중)
- 각 후보가 어떤 실수를 줄이고 어떤 실수를 늘리는지 한 줄씩 쓴다. 선택은 결정 절에.

## 2. 기준선 먼저
- 가장 단순한 것 하나: 다수 클래스·평균 예측, 규칙 하나, 로지스틱 회귀나 얕은 트리.
- 분할은 probe-data-check의 데이터 계약을 따른다. 식별자는 데이터에 보존하고, 입력 사용 여부는 계약대로.
- 전처리는 모델과 같은 파이프라인 안에 두고 학습 분할로만 fit한다.
- 학습·검증 점수를 나란히 출력한다. 차이가 크면 과적합이다.
- **내부 holdout은 이 단계에서 평가하지 않는다.** 제출용 test 추론은 해도 된다(라벨이 없어 점수를 볼 수 없다).
- seed를 고정한다. 분류는 혼동행렬, 회귀는 잔차 요약(값 구간별 치우침)을 결과 파일로 남긴다.
- 실험 절 0번 줄로 기록한다.

## 3. 실험 한 번 = 가설 하나
- 바꾸기 전에 한 줄: `가설: X를 바꾸면 Y가 좋아진다, 이유 Z`
- 한 번에 하나만 바꾸고, 학습·검증으로만 비교한다. 결과를 실험 절에 한 줄 추가한다:
```
| # | 바꾼 것 | 가설 | 지표(검증) | 기준선 대비 | 판정 | 근거(명령·결과 파일·코드 파일:줄) |
```
- 판정은 다섯 중 하나:
  - `keep`: 같은 조건에서 개선을 확인
  - `discard`: 나빠짐
  - `inconclusive`: 차이가 잡음 수준. 양성이 적으면 지표 옆에 양성 개수를 적고, 잡음인지는 부트스트랩 범위나 여러 시점 분할로 본다
  - `crash`: 실행 실패
  - `invalid`: 비교 조건이 바뀜, 기준선 없음, 짧은 시험 실행을 성능처럼 제시
- 실패와 무효도 남긴다. 여러 번 시도해서 좋게 나온 것만 보고하지 않는다.

## 4. 오류를 보고 다음 수를 정한다
- 검증 분할에서 틀린 사례를 FP/FN(회귀는 큰 잔차)으로 나눠 공통점을 찾는다: 설비·공정·제품·기간·값 구간.
- 다음 실험은 그 오류 묶음을 줄일 가설로만 고른다.
- 변수 중요도와 상관계수는 관계의 크기이지 원인이 아니다. 산점도나 그룹별 표로 확인하고, 원인 해석은 `[추론]`으로 쓴다.
- 기준선이 왜 실패하는지 설명된 뒤에만 더 복잡한 모델을 쓴다.

## 5. 확정과 holdout 평가
- 70%(남은 시간 30%)가 지나면 새 실험을 먼저 제안하지 않고 현재 최선의 확정·검증을 우선한다. 사용자가 새 실험을 요청하면 AGENTS 8을 따른다.
- 실험 절을 보여주고 사용자가 최종 모델·변수·임계값을 고른다.
- 확정한 뒤 내부 holdout을 **한 번만** 평가하고, 그 값을 최종 성능으로 결과 파일에 남긴다.
- holdout 결과가 기대와 달라도 그걸 보고 다시 고르지 않는다. 차이는 한계로 기록한다.
- (선택) 확정한 설정 그대로 학습+검증(+holdout) 전체로 다시 학습해 제출용 test를 다시 추론할 수 있다. 할지는 최종 선택 때 같이 묻는다. 했으면 제출 파일 형식 확인을 다시 하고, 이 모델의 성능은 따로 잴 수 없으니 holdout 값을 참고치로 적는다.

## 금지
- holdout 점수를 보고 모델·변수·임계값을 다시 고르기.
- 미래 정보나 타깃에서 파생된 컬럼을 입력으로 쓰기.
- 설명할 수 없는 파생변수를 대량으로 만들기.
